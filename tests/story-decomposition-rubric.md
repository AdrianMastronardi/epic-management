# Story decomposition evaluation rubric

Use with [story-decomposition-cases.md](story-decomposition-cases.md) when changing decomposition, dependency, or publication guidance. Give an evaluator the input cases and relevant skill instructions without this rubric, prior evaluation reports, or expected decisions: copy only the cases file and the skill's `SKILL.md`, `references/`, and `assets/` into an isolated directory, because an evaluator working in this repository can open the rubric and reports beside the cases. After the evaluator produces its plan, compare observable decisions with the criteria below. Record the evaluated revision, actual decisions, pass/fail results, and limitations in a temporary report; an assessed report may then be retained under `tests/` as evidence, excluded from later evaluator inputs. A manual walkthrough is useful but must not be reported as an independent agent evaluation. These cases do not replace the structural validator tests.

Across all cases, the checkpoint must distinguish native edges from documented conditions and explain the release evidence. A documented condition remains mandatory for its stated phase. Evaluation performs no remote mutations and records no fabricated approvals. Equivalent wording or a different diagram layout is acceptable; grade decisions and constraints, not phrases or headings.

In case 6's not-planned variant, the evaluator must identify the closed producer as a conflict requiring evidence or a plan correction before affected native actions. Merely proposing a new edge to that closed producer as the operational blocker fails this criterion, even if the body also records uncertainty.

In case 6's other variants, a linked merged pull request is insufficient when the output is absent from the consumer's base branch, required checks fail, or the delivery was reverted. Keep the gate unresolved and treat the closed producer as a conflict requiring evidence or a plan correction; neither mark the prerequisite satisfied nor add an edge to the closed producer as a substitute.

Cases 1 to 6 state each constraint's phase almost directly, so they check that the projection policy is applied. Cases 7 to 10 give repository and source facts without that classification; weigh them more heavily when judging whether a change improves planning decisions.

Cases 11 to 17 exercise the complete-graph policy through hidden gates, documented-only and transitive cycles, partial publication, cross-EPIC uncertainty, legacy prose, and source conflicts. Case 18 is a control for false dependencies from informational navigation and parentage.

When a change adds or alters policy, run the same cases against the previous release as a baseline and report both results. A case that both revisions resolve identically is not evidence for the change. One run per revision shows that the behavior is reachable, not that it is reliable; say how many runs the report covers.
